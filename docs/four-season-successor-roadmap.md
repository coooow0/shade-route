# 그늘길 후속: 사계절 쾌적 도보 경로 로드맵

> 작성일: 2026-08-05  
> 상태: 출시된 서울 버전의 후속 검토 문서. 현재 제품 범위나 구현 완료 사항을 뜻하지 않는다.

## 1. 후속 제품의 방향

현재 그늘길은 여름철 서울에서 건물 그늘을 더 많이 이용하는 경로를 찾는다. 후속 제품은 이 기능을 **출발 시각의 날씨에 맞는 쾌적한 도보 경로**로 확장한다.

- 더운 날은 햇빛 노출을 줄인다.
- 추운 날은 실제 햇빛이 있을 때 양지를 더 이용한다.
- 날씨가 순하거나 해가 졌을 때는 불필요한 우회를 없애고 빠른 길을 선택한다.
- 자동 추천을 기본으로 제공하되, 사용자가 경로 모드를 직접 바꿀 수 있게 한다.

핵심 제품 문장은 다음과 같다.

> 지금 날씨와 출발 시간에 맞는 편안한 걸음길을 비교해요.

## 2. 계절은 사용자가 선택하지 않는다

`봄·여름·가을·겨울`은 경로 선택의 직접적인 기준이 아니다. 같은 4월에도 낮에는 덥고 저녁에는 추울 수 있다. 앱은 출발 지점·시각의 체감온도, UV, 낮·밤, 직달일사를 보고 경로를 추천한다.

사용자에게는 계절 선택기 대신 다음 정보를 보여준다.

- `지금은 체감 31°·UV 높음이에요. 그늘이 많은 길을 추천해요.`
- `지금은 체감 6°이고 햇빛이 충분해요. 양지가 많은 길을 추천해요.`
- `해가 진 시간이에요. 빠른길을 추천해요.`

추천 이유를 노출하면 자동화가 임의적으로 보이지 않고, 잘못된 추천을 사용자가 바로 수정할 수 있다.

## 3. 날씨 기준

### 3.1 UV 기준

UV 등급은 [기상청 생활기상정보 지수 기준](https://www.weather.go.kr/w/resources/jsp/life/jisu_data_table.html)을 그대로 사용한다.

| UV | 표시 | 기본 경로 영향 |
| ---: | --- | --- |
| 3 미만 | 낮음 | UV 때문에 경로를 바꾸지 않음 |
| 3 이상·6 미만 | 보통 | 균형 경로 후보 |
| 6 이상·8 미만 | 높음 | 그늘우선 |
| 8 이상·11 미만 | 매우 높음 | 그늘우선+주의 문구 |
| 11 이상 | 위험 | 그늘우선+강한 주의 문구 |

UV에 대한 `그늘우선`은 보호제·의복·야외활동 조정을 대체하지 않는다. 건물 그늘이 흐린 날의 산란 UV까지 차단한다고 안내해서도 안 된다.

### 3.2 체감온도 기준

체감온도에는 모든 보행자에게 보편적으로 적용할 `쾌적·불쾌적` 경계값이 없다. 따라서 다음 구간은 기상 특보 기준이 아니라 **그늘길의 초기 제품 기준**으로 다룬다.

| 체감온도 | 앱 내부 상태 | 기본 경로 영향 |
| ---: | --- | --- |
| 10°C 이하 | 추움 | 햇빛이 충분하면 햇빛우선 |
| 10°C 초과·27°C 미만 | 중립 | 빠른길 |
| 27°C 이상·30°C 미만 | 더움 | 균형 |
| 30°C 이상 | 매우 더움 | 그늘우선 |

기상청 폭염 영향예보는 일 최고 체감온도 31°C부터 `관심` 단계로 다룬다. 앱은 위험 경고가 아니라 경로 추천이므로 30°C에서 한 발 먼저 그늘을 추천한다. `체감 30°C=폭염`처럼 공식 경보로 표현하지 않는다. 참고: [기상청 폭염 영향예보 안내](https://www.weather.go.kr/wnuri_help/doc/heatwave_leaflet_kor.pdf)

10°C는 햇빛우선을 시작하는 가설이다. 출시 후 사용자가 추천을 그대로 선택하는지 측정하고, 8·12°C 범위에서 조정한다.

### 3.3 햇빛이 실제로 있는지 확인하는 기준

추운 날이라도 흐리면 햇빛우선의 편익이 거의 없다. 햇빛우선은 다음 조건을 모두 만족할 때만 자동 추천한다.

- 낮임(`is_day = true`)
- 체감온도 10°C 이하
- UV 6 미만
- 직달일사(`direct_normal_irradiance`) 120W/㎡ 이상

[Open-Meteo 공식 문서](https://open-meteo.com/en/docs)는 직달일사가 120W/㎡를 넘는 시간을 일조 시간으로 계산한다. 체감온도는 기온·습도·바람·일사를 결합한 Open-Meteo의 `apparent_temperature`를 사용한다.

## 4. 자동 추천 규칙

앱은 출발 지점과 선택한 출발 시각의 날씨를 불러와 다음 순서로 판단한다. 위에 있는 조건이 우선한다.

```text
1. 밤이면 빠른길
2. UV ≥ 6 또는 체감온도 ≥ 30°C이면 그늘우선
3. 체감온도 ≤ 10°C, UV < 6, 직달일사 ≥ 120W/㎡이면 햇빛우선
4. UV ≥ 3 또는 체감온도 ≥ 27°C이면 균형
5. 나머지는 빠른길
```

충돌 상황은 다음과 같이 처리한다.

| 상황 | 처리 |
| --- | --- |
| 추운데 UV가 6 이상 | 그늘우선. 사용자는 햇빛우선으로 바꿀 수 있음 |
| 추운데 흐림 | 빠른길. 의미 없는 햇빛 우회를 만들지 않음 |
| 밤에 UV·온도 오류값 수신 | 낮·밤 판정을 우선하고 빠른길 |
| 날씨 요청 실패 | 균형 또는 빠른길. 자동 추천 이유를 만들지 않음 |
| 비·눈·결빙 위험 | 햇빛·그늘보다 보행 안전 규칙을 우선. 별도 설계 필요 |

날씨가 경계값을 오갈 때 추천이 계속 바뀌지 않도록 히스테리시스를 둔다.

- 그늘우선 진입: 체감 30°C 이상 / 해제: 28°C 미만
- UV 그늘우선 진입: UV 6 이상 / 해제: UV 5 미만
- 햇빛우선 진입: 체감 10°C 이하 / 해제: 12°C 초과

경로를 탐색한 뒤에는 해당 결과의 추천 모드를 고정한다. 탐색 중 날씨 업데이트로 선택 경로가 바뀌지 않는다.

## 5. 경로 모드

| 모드 | 목적 |
| --- | --- |
| 빠른길 | 소요 시간과 거리를 우선 |
| 균형 | 우회 시간과 햇빛·그늘 편익을 함께 고려 |
| 그늘우선 | 햇빛 노출을 더 강하게 회피 |
| 햇빛우선 | 직사광선이 닿는 구간을 더 많이 선택 |

햇빛우선은 그늘우선의 가중치에 단순히 마이너스를 붙이지 않는다. 음수 간선 비용은 순환·과도한 우회를 만들 수 있다. 모든 간선 비용을 양수로 유지하고, 예상 그늘 시간을 추가 비용으로 더하는 방식을 쓴다.

```text
햇빛우선 간선 비용
= 이동 시간
+ 그늘 구간 예상 시간 × 그늘 페널티
+ 우회 제한 페널티
```

햇빛 편익이 작은데 소요 시간이 크게 늘어나면 햇빛우선 후보에서 제외한다. 보행 가능 판정, 출입 제한, 에스컬레이터 방향, fallback 도로 페널티 등 현재의 안전 정책은 모든 계절 모드에 동일하게 적용한다.

## 6. 현재 구현과의 차이

현재 `src/domain/weather/currentWeather.ts`는 다음 부분까지 구현했다.

- UV 등급을 기상청 기준으로 분류한다.
- 낮에 UV 6 이상 또는 체감온도 30°C 이상이면 그늘우선을 추천한다.
- UV 3 이상 또는 체감온도 27°C 이상이면 균형을 추천한다.
- 밤에는 빠른길을 추천한다.

후속 제품에서는 다음 변경이 필요하다.

- `direct_normal_irradiance`를 날씨 응답과 런타임 검증에 추가한다.
- `sunny` 또는 `maxSun` 경로 모드를 추가한다.
- 서울 대표 좌표의 현재 날씨 대신 경로 지역·출발 시각의 날씨를 사용한다.
- `30분 뒤`·`1시간 뒤`에는 현재값이 아닌 해당 시각의 예보값을 적용한다.
- 햇빛우선 경로의 비교 문구와 지도 색상을 추가한다.

Open-Meteo로 사용자의 정확한 출발지 좌표를 직접 보내는 방식은 현재의 `사용자 위치를 저장·외부 전송하지 않는다`는 방향을 바꾼다. 프로토타입은 도시 대표 좌표를 쓰고, 전국 서비스는 격자화된 좌표와 서버 프록시·캐시를 사용하는 안을 별도 위협 모델로 검토한다.

## 7. UI 방향

초기 후속 버전은 현재의 비교 구조를 유지한다.

- 자동 추천 사유를 날씨 카드와 결과 표에 보여준다.
- 사용자는 `빠른길·균형·그늘우선·햇빛우선` 중 하나를 선택할 수 있다.
- 여름에는 햇빛 절약 시간과 예상 그늘 비율을 강조한다.
- 겨울에는 양지 추가 시간과 예상 햇빛 비율을 강조한다.
- 모든 수치는 예상치로 표시하고, 현장 공사·가로수·건물 데이터의 한계를 계속 안내한다.

앱 이름 `그늘길`은 초기에 유지할 수 있다. 다만 앱 소개는 `햇빛을 피하는 길`에서 `날씨에 맞는 편안한 길`로 넓힌다. 겨울 기능의 인지도가 낮거나 이름 때문에 사용자가 혼란을 보이면 재브랜딩을 다시 검토한다.

## 8. 전국·App Store 확장

사계절 추천과 전국 확장을 한 번에 구현하지 않는다. 원인을 분리해야 추천 실패와 데이터 실패를 각각 측정할 수 있다.

### 1단계: 서울 사계절 실험

- 현재 경로 데이터에 햇빛우선 모드를 추가한다.
- 추천 수락률, 사용자의 모드 변경률, 실제 체감 피드백을 측정한다.
- 온도 경계값과 우회 제한을 서울 데이터로 보정한다.

### 2단계: 도시 하나 추가

- 피드백 수요와 OSM 건물·보행로 품질을 같이 보고 부산·인천·대전 등에서 하나를 선택한다.
- 도시별 전처리 데이터의 크기, 건물 높이 누락률, 경로 성공률, 결과 시간을 측정한다.
- 이 단계에서 도시별 번들 방식의 한계를 확인한다.

### 3단계: 전국 온디맨드 데이터

- 필요한 지역 타일만 CDN에서 받는다.
- 릴리스 버전·파일 크기·SHA-256을 고정한 서명 매니페스트를 사용한다.
- 날씨와 지역 데이터를 서버 프록시에서 격자 단위로 캐시한다.
- 사용자의 정확한 위치를 로그에 남기지 않는다.

### 4단계: 독립 iOS 앱

App Store 버전은 전국 데이터 제공, 실기기 위치 동작, 맵 디자인, 재방문 가치를 검증한 뒤 진행한다. 독립 앱은 심사·개인정보 표시·백그라운드 위치·지도 라이선스·날씨 API 상용 계약을 새로 검토해야 한다.

현재 React 코어를 재사용할지, React Native나 SwiftUI로 다시 만들지는 이 단계에서 결정한다. 설치형 앱의 필요성을 검증하기 전에 네이티브 재작성을 시작하지 않는다.

## 9. 측정 지표

기준을 고정한 뒤 다음 지표로 조정 여부를 판단한다.

- 자동 추천 모드 수락률
- 자동 추천 후 다른 모드로 바꾸는 비율
- 체감온도·UV·직달일사 구간별 경로 완주·이탈률
- 예상 햇빛·그늘 비율과 사용자 피드백의 차이
- 햇빛우선의 양지 증가 시간과 추가 보행 시간
- 도시별 검색 성공률, 경로 성공률, 계산 시간
- 현재 그늘길의 재방문율과 독립 앱 요청 수요

개인정보 원칙은 현재와 같게 유지한다. 출발지·도착지 좌표, 검색어, 실시간 위치 이력을 분석 이벤트에 담지 않는다.

## 10. 필수 보안·정확도 원칙

- 날씨 API 응답은 현재처럼 타입·범위를 검증한다. 직달일사도 상한과 하한을 둔다.
- 격자 좌표와 캐시 키는 사용자 위치를 불필요하게 정밀하게 복원할 수 없도록 설계한다.
- 배포 아티팩트·CDN 타일은 스키마, 크기, 개수, 해시, 릴리스 ID를 검증하고 불일치하면 경로를 만들지 않는다.
- 그늘·햇빛 결과는 모두 예상치로 표시한다. 실제 안전, 날씨, 공사, 가로수를 반영한 전문 내비게이션으로 과장하지 않는다.
- 비·눈·결빙을 다룰 때는 `양지를 많이 지나니 안전하다`라고 단정하지 않는다. 실시간 노면 상태를 확인하지 못하므로 결빙 회피 기능은 별도 데이터가 있을 때만 제공한다.

## 11. 필요한 테스트

### 규칙 단위 테스트

- UV: 2.9, 3, 5.9, 6, 7.9, 8, 10.9, 11
- 체감온도: 9.9, 10, 10.1, 26.9, 27, 29.9, 30
- 직달일사: 119, 120W/㎡
- 낮·밤 변경과 날씨 API 실패
- 차가움+UV 높음, 차가움+흐림 등 충돌 규칙
- 히스테리시스 진입·해제 경계

### 경로 통합 테스트

- 햇빛우선이 빠른길보다 양지 시간을 늘리는지 확인
- 햇빛이 없거나 변화가 없을 때 과도한 우회를 생성하지 않는지 확인
- 모든 모드가 동일한 보행 안전·접근 제한을 적용하는지 확인
- 출발 시각을 30분·1시간 뒤로 바꾸면 태양 위치와 날씨 예보가 함께 바뀌는지 확인

### E2E·실기기 테스트

- 자동 추천 사유 표시 후 사용자가 다른 모드로 바꿀 수 있는지 확인
- 맑고 추운 날, 흐리고 추운 날, 덥고 UV가 낮은 날, 선선하고 UV가 높은 날을 각각 확인
- 320px·390px 화면에서 네 경로 비교가 넘치거나 선택을 방해하지 않는지 확인
- iOS·Android에서 시각대, 현재 위치, 타임스탬프 변환이 같은 결과를 내는지 확인

## 12. 실행 순서

1. 서울 외 데이터를 늘리기 전에 햇빛우선 간선 비용과 경계값 테스트를 만든다.
2. 출발 시각에 맞는 체감온도·UV·직달일사를 불러오고 자동 추천 규칙을 구현한다.
3. 햇빛우선 경로와 비교 UI를 붙인다.
4. 서울에서 추운 날의 추천 수락률·우회 비용·현장 피드백을 모은다.
5. 데이터 그래프와 건물 품질을 검증할 다음 도시 하나를 선정한다.
6. 도시별 실험에서 성공률과 운영 비용을 확인한 뒤 전국 온디맨드 구조를 설계한다.
7. 재방문 수요와 독립 앱 요청이 확인되면 App Store 버전을 결정한다.

## 13. 아직 결정하지 않은 사항

- `햇빛우선` 및 전체 모드의 최종 이름
- 체감온도 10°C 진입 기준과 12°C 해제 기준의 실제 보정값
- 햇빛우선에 허용할 최대 우회 시간·비율
- 비·눈·미세먼지·강풍을 포함한 보행 안전 추천 범위
- 두 번째 지원 도시
- 전국 타일 CDN·서명·캐시 운영 구조
- App Store 버전의 기술 스택과 재브랜딩 여부

## 14. 현재 판단

다음 후속 작업은 `전국 데이터 이식`이 아니라 **서울 데이터에서 햇빛우선 경로를 실험하는 것**이다. 이 실험은 사계절 가치, 추천 기준, 우회 허용량을 가장 작은 변경으로 검증한다. 결과가 좋을 때 도시를 하나 늘리고, 그 다음에 전국·App Store 확장을 판단한다.
