# 전국 확대와 사용자 피드백 검토 노트

> 2026-07-24 대화에서 정리한 초기 검토. 결정 문서가 아니라 다음 논의를 위한 배경 자료다.

## 1. 전국 확대 — 프로토타입에서는 부담이 큼

지금 구조상 정직하게 확대하기가 쉽지 않다.

### 걸리는 지점

- **데이터 부피**: 서울은 812 타일·115k way·5만 장소로 앱 번들에 다 들어온다. 전국은 대략 15–25배 규모다. `.ait` 하나에 담을 수 없고, 앱 시작 시 다 로드하는 것도 불가능하다.
- **무결성 잠금 방식과 충돌**: PR3에서 manifest·타일·장소 인덱스를 SHA-256으로 번들에 못 박아 두는 fail-closed 설계다. 온디맨드 CDN 방식으로 가려면 이 아키텍처를 뜯어야 한다 (서버 필요).
- **건물 높이 데이터 품질**: 서울 밖은 OSM 건물 높이가 훨씬 성글다. fallback 12m로 계산되는 비율이 커지고 그늘 예측의 정확도가 떨어진다.
- **PROJECT_CONTEXT.md에 남긴 원칙**: "서울·3km 제한을 임의로 넓히지 않는다"가 명시돼 있다 (챌린지 완성도를 위해 스코프를 잠근 결정). 확대는 그 원칙을 바꾸는 제품 결정이다.

### 현실적 절충안

- **A. 도시 몇 개 추가** (부산·인천·대전·대구 등)
  - 서울과 같은 방식으로 도시별 preprocessed 번들 생성 → 사용자가 도시 선택
  - 데이터 부피는 도시 수만큼 배로 늘지만, 사용자는 자기 도시만 쓰니 앱 부담이 없다
  - 단 도시별로 데이터 생성 파이프라인·QA가 필요하다
- **B. 서버 도입해서 전국 온디맨드**
  - CDN에서 필요한 타일만 서명 붙여 내려받는 구조
  - 인프라 상당량 필요, 챌린지 마감(2026-07-29)까지는 불가능한 규모다

### 지금의 판단

현재 챌린지 마감 안에는 A조차 어렵다. 챌린지 이후 P2/P3 항목으로 "다음 도시 추가" 로드맵을 두는 편이 낫다. 대신 지금 시점에는 사용자에게 **"다른 도시도 원해요?"**를 피드백 항목으로 넣어 수요 근거를 모으는 것이 실용적이다.

## 2. 정확도 피드백 — 지금 붙일 수 있음

훨씬 작은 스코프. 구현 방식은 저장소 선택에 달렸다.

### 선택지

- **1. Google Form / Tally 링크만**
  - 결과 화면 하단에 "이 경로가 실제 그늘과 맞았나요?" 버튼 → 새 창에 폼
  - 코드 최소. 응답 수집·집계 다 외부가 처리
  - 단 사용자가 앱을 이탈해야 함
- **2. 임베드 폼 + 서버리스 웹훅** (Google Sheets Apps Script, Cloudflare Worker 등)
  - 앱 안에 좋음/보통/나쁨 3개 버튼 + 선택형 메모
  - 자동으로 라우트 메타(모드·거리·그늘%·요청 시각)와 같이 전송
  - 개인정보(위치·검색어)는 안 보냄
- **3. 백엔드 도입**
  - 오버킬. 현재 "별도 백엔드 없음" 원칙과 어긋남

### 현재 추천: 2번

- 사용자 이탈 없이 앱 안에서 완결된다
- 라우트 메타를 자동 부착해서 정성 피드백을 데이터로 볼 수 있다 (도시 확대 결정에도 근거가 된다)
- 인프라는 Google Sheets 웹훅 정도라 몇 시간이면 된다. "서버 없음" 원칙에 근접 (webhook URL 하나만 환경변수로)
- 개인정보 최소: 위치·검색어·아이디 없이 라우트 결과 요약만

### 수집 항목 초안

- 만족도 (좋음/보통/나쁨)
- 자유 메모 (선택)
- 라우트 모드 (빠른길/균형/그늘우선)
- 거리·소요 시간·예상 그늘% (숫자만)
- 요청 시각
- "다른 도시도 원해요? 어떤 도시?" (선택)

## 3. 진행 옵션

1. **피드백만 2번 방식으로 붙이고, 전국 확대는 여기 문서에 로드맵으로만 기록** ← 현재 시점 추천
2. 피드백 붙이고, 확대는 도시 하나(예: 부산)만 실험적으로 파이프라인 돌려서 데이터 크기·품질 감 잡기
3. 지금은 아무것도 안 하고 아이디어만 정리 (챌린지 이후 재개)

2번을 갈 경우 웹훅 대상(Google Sheets vs Cloudflare Worker vs Airtable) 선택이 남아 있다.

## 4. 진행 기록

### 2026-07-25 · 피드백 위젯 구현 (선택지 1 채택)

- `RouteFeedback` 위젯을 결과 시트 하단에 마운트했다. 만족도(좋음/보통/나쁨), 자유 메모, "다른 도시도 원해요?" 필드를 한 폼에 담고 `보내기` 한 번으로 웹훅 POST가 나간다.
- 클라이언트 (`src/domain/feedback/feedbackClient.ts`): `Content-Type: text/plain`으로 CORS preflight 회피, 타임아웃·abort 지원, 메모 500자·도시 60자 상한.
- `localStorage`의 `shade-route:feedback:{pathKey}`로 같은 경로에서는 두 번째 제출을 막는다.
- 환경변수 `VITE_FEEDBACK_WEBHOOK_URL`이 비어 있으면 위젯 자체를 렌더링하지 않아 dev·오픈소스 fork에서는 조용하다.
- 커밋: `feat: collect route accuracy feedback via opt-in webhook`.

### 2026-07-27 · Google Sheets 연동 확인

- 웹훅 대상은 Google Apps Script + Google Sheets로 세팅했다. 세팅 절차는 [`docs/feedback-webhook.md`](./feedback-webhook.md).
- 실제 URL은 로컬 `.env.local` (gitignore됨) 에만 두고 커밋하지 않는다.
- 세팅 중 발견한 함정 두 가지:
  1. **Apps Script `console.log`가 성공 실행에서는 인라인 실행 로그에 안 보인다.** GCP 프로젝트 연결이 없으면 Cloud Logging으로만 흘러가서 확인이 어렵다. 진단용 로그는 `Logger.log`로 심어야 성공/실패 모두에서 실행 상세에 나타난다.
  2. **`getSheetByName("Sheet1")`이 로케일에 따라 null.** 한국어 계정 스프레드시트는 기본 탭이 `시트1`인 경우가 있다. 이름 매칭 대신 `SpreadsheetApp.getActive().getSheets()[0]`으로 첫 번째 시트를 잡는 편이 이름 변경에 강하다. Apps Script 코드는 이 형태로 남겨 두었다.
- 시트에 정상적으로 행이 쌓이는 것을 브라우저 콘솔 `fetch` 테스트와 실제 위젯 클릭 두 방법으로 확인했다.
- 지금부터 쌓이는 응답은 다음 결정(예: 어느 도시부터 확장할지, 그늘 예측 정확도가 낮은 조건이 뭔지)에 근거로 쓴다.
