# 보안 개선 PR 1 — WebView 자원 고갈 방어

- 작성일: 2026-07-15
- 상태: 구현 및 전체 품질 게이트 검증 완료
- 범위: 클라이언트 루팅 데이터, 그래프, 그늘 판정, Leaflet 렌더링, 상세 길안내, 서울 서비스 영역 검증
- 비범위: 보행 규칙 정확도(PR 2), 데이터 아티팩트 무결성·Web Worker 분리(PR 3)

## 결론

PR 1은 비정상적으로 복잡한 루팅 데이터가 토스 WebView의 CPU, 메모리, DOM, Leaflet 레이어를 무제한으로 늘리는 경로를 차단한다. 데이터를 큰 객체로 확장하기 전에 작업량을 검증하고, 그래프·그늘·경로·UI 각 단계에 별도 상한을 두었다.

현재 `public/data` 스냅샷의 812개 루트 타일은 모두 compact schema 2이며, 가장 밀집한 단일 타일과 36타일 경로 영역도 새 상한 안에 있다. 서울·3km 제한, 위치 미저장, 외부 장소 API 미사용 정책은 바꾸지 않았다.

## 발견 사항별 근거와 공격 경로

### DSC-003 — 고차수 그래프 인접 배열 폭증 (Medium)

- 수정 전 위치: `src/domain/routing/graph.ts:69-78`
- 방어 코드: [`graph.ts`](../../src/domain/routing/graph.ts#L69), [`resourceLimits.ts`](../../src/domain/routing/resourceLimits.ts#L10)
- 공격 조건과 경로: 공격자가 오염된 타일에 하나의 노드와 수만 개 노드를 연결한 way를 넣는다. 앱이 타일을 읽어 `buildGraph` → `makeAdjacency` 순으로 처리하면 배열 spread가 매 간선마다 기존 배열을 복사해 WebView CPU·메모리를 고갈시킨다.
- 코드 근거: 수정 전에는 `adjacency.set(node, [...old, edge.id])`가 반복됐다. 현재는 불변 연결 리스트에 `O(E)`로 쌓은 후 한 번만 배열로 평탄화하고, 노드 차수가 64를 넘으면 즉시 중단한다.
- 오탐 가능성: 정상 스냅샷의 전체 그래프 최대 차수는 11이므로 64 상한이 정상 데이터를 막을 가능성은 낮다. 다만 특수 데이터 갱신이 있을 때는 재측정이 필요하다.
- 최소 수정·테스트: 선형 인접 구조와 차수 상한. `graphNodeDegree + 1` star 그래프 거부, 정상 그래프 생성 회귀 테스트.

### DSC-004 — 연결 요소별 전체 간선 재스캔 (Medium)

- 수정 전 위치: `src/domain/routing/graph.ts:164-194`
- 방어 코드: [`graph.ts`](../../src/domain/routing/graph.ts#L165)
- 공격 조건과 경로: 서로 떨어진 작은 way를 대량으로 넣은 타일을 로드하면, 연결 요소 `C`번마다 전체 간선 `E`개를 `filter`했다. 결과는 `O(C×E)` CPU 소모와 다수의 임시 배열이다.
- 코드 근거: 현재 BFS가 방문한 간선 ID를 같이 수집하여 전체 간선 재스캔을 없앰고, 513번째 연결 요소에서 중단한다.
- 오탐 가능성: 서울 OSM에 작은 분리 요소가 있을 수 있다. 그러나 정상 경로 영역의 실측 최대는 86이며 512와 간격이 크다.
- 최소 수정·테스트: 간선 ID 수집 + 연결 요소 상한. 513개 분리 요소 거부와 정상 연결 요소 분할 테스트.

### DSC-005 — Leaflet 레이어 증폭 (Medium)

- 수정 전 위치: `src/components/leafletRouteMap.ts:102-138`
- 방어 코드: [`leafletRouteMap.ts`](../../src/components/leafletRouteMap.ts#L106), [`router.ts`](../../src/domain/routing/router.ts#L172)
- 공격 조건과 경로: 매우 잘게 쪼개진 경로가 생성되면 세그먼특 casing 1개와 색상 선 1개, 즉 `2N`개 Leaflet 레이어가 생성된다. 지도 렌더링과 이벤트 처리가 메인 스레드를 점유할 수 있었다.
- 코드 근거: casing을 multi-polyline 1개로, connector·그늘·햇빛 그룹을 각각 1개로 묶어 세그먼트 수와 무관하게 최대 4개만 생성한다. 요약 전 경로도 2,000 세그먼트 초과를 거부한다.
- 오탐 가능성: 세그먼트를 묶여도 각 multi-polyline의 선 조각은 유지되므로 경로 형상은 바뀌지 않는다. 색상 기준은 기존 `segmentStyle` 규칙을 유지한다.
- 최소 수정·테스트: multi-polyline 그룹화 + 경로 세그먼트 상한. 300 세그먼트 입력에서 `L.polyline` 호출이 수정 전 600회, 수정 후 4회인 테스트.

### DSC-006 — 접힌 상세 길안내 DOM (Low)

- 수정 전 위치: `src/components/RouteDirections.tsx:99-133`
- 방어 코드: [`RouteDirections.tsx`](../../src/components/RouteDirections.tsx#L67), [`directions.ts`](../../src/domain/routing/directions.ts#L166)
- 공격 조건과 경로: 긴 경로가 많은 회전 단계를 만들면 사용자가 상세 안내를 펼치지 않아도 전체 `<li>` DOM이 생성됐다. 각 항목의 `findIndex`로 추가 `O(N²)` 탐색도 발생했다.
- 코드 근거: 접힌 상태에서 목록을 mount하지 않고, index를 직접 ARIA 순서로 쓴다. 400단계를 넘으면 펼쳐도 목록 대신 제한 안내를 보여준다. 길안내 그룹 생성도 배열 spread 반복에서 선형 연결 리스트로 바꾸었다.
- 오탐 가능성: 400단계 이상을 세부 텍스트로 보여주지 않으므로 기능 제한은 있다. 다만 경로 자체와 지도는 보존되며, 정상 사용자에게는 이 정도 단계 수가 실질적으로 유용하지 않다.
- 최소 수정·테스트: 지연 mount + 400단계 상한 + 선형 그룹화. 접힌 DOM 0개, 펼침 후 정상 목록, 401단계 목록 미생성 테스트.

### DSC-011 — compact 건물 좌표 확장 (Medium)

- 수정 전 위치: `src/domain/routing/tileRouteData.ts:100-188, 246-257`
- 방어 코드: [`tileRouteData.ts`](../../src/domain/routing/tileRouteData.ts#L103), [`resourceLimits.ts`](../../src/domain/routing/resourceLimits.ts#L10)
- 공격 조건과 경로: 소수의 compact 건물에 매우 긴 좌표 배열을 넣어 파일 크기 제한은 피하면, `expandCoordinates` 가 숫자 배열을 대량의 `{lat, lon}` 객체로 바꾸며 메모리를 크게 늘릴 수 있었다.
- 코드 근거: way당 512포인트, 건물당 256포인트, 타일·경로 전체 수량 상한을 compact 상태에서 계산한다. 모든 검증을 통과한 후에만 객체로 확장한다.
- 오탐 가능성: 제한을 초과하는 실제 복잡 건물이 생길 수 있다. 현재 전체 스냅샷의 건물별 최대는 117포인트로 256 이하이다.
- 최소 수정·테스트: 확장 전 수량 예산 검사. 건물별·타일별·경로별 포인트 초과 거부 테스트와 실제 타일 로드 테스트.

### DSC-012 — legacy schema 1 확장 경로 (Low)

- 수정 전 위치: `src/domain/routing/tileRouteData.ts:103-113, 246-252`
- 방어 코드: [`tileRouteData.ts`](../../src/domain/routing/tileRouteData.ts#L179)
- 공격 조건과 경로: 타일이 schema 1이면 compact 수량 예산을 거치지 않고 이미 확장된 Overpass 객체를 받아들였다. 오염된 legacy 타일은 더 많은 객체 파싱 비용을 유발할 수 있었다.
- 코드 근거: 루트 타일 decoder에서 schema 1 분기를 제거했고 schema 2만 반환한다. 타일 manifest의 schema 1은 별개 포맷으로 유지된다.
- 오탐 가능성: 과거 schema 1 루트 타일을 재배포하면 로드가 실패한다. 현재 812개 루트 타일이 모두 schema 2임을 확인했다.
- 최소 수정·테스트: schema 2만 허용. schema 1 거부와 실제 schema 2 타일 호환성 테스트.

### DSC-031 — 겹친 그늘 후보 폭증 (Medium)

- 수정 전 위치: `src/domain/routing/shadow.ts:45-49`
- 방어 코드: [`shadow.ts`](../../src/domain/routing/shadow.ts#L46)
- 공격 조건과 경로: 여러 건물의 그늘 bounding box가 한 지점에 겹치도록 조작한다. 경로 샘플 지점마다 RBush 결과의 모든 hull에 point-in-polygon을 반복하며 CPU를 소모한다.
- 코드 근거: RBush 결과를 한 번 검색한 후 512개를 넘으면 hull 검사 전에 중단한다.
- 오탐 가능성: 고층 밀집 지역에서 후보가 많을 수 있으나, 512개 동시 겹침은 정상 도시 형상에 대해 보수적으로 높은 한도다.
- 최소 수정·테스트: 지점당 후보 상한. 513개 겹침 거부, 일반 그늘 판정 회귀 테스트.

### DSC-037 — 서울 경계 반복 스캔 (Low)

- 수정 전 위치: `src/domain/location/serviceArea.ts:3-40`
- 방어 코드: [`serviceArea.ts`](../../src/domain/location/serviceArea.ts#L10)
- 공격 조건과 경로: 장소 인덱스에 서울 경계 근처의 후보가 많으면, 각 후보의 tolerance 좌표마다 약 1,495개 경계 간선을 전체 스캔했다. 정상 데이터로도 검색 초기화가 느려질 수 있었다.
- 코드 근거: 경계를 128개 위도 버킷에 사전 인덱싱하고, bounding box 밖의 좌표를 즉시 제외한다. 선택된 버킷의 간선만 기존 ray-crossing 공식으로 검사한다.
- 오탐 가능성: 공간 인덱스가 경계 판정을 바꾸는 회귀 위험이 있다. 48×48 격자 2,304개 좌표를 기존 전체 스캔 참조 구현과 비교해 결과가 모두 같음을 테스트했다.
- 최소 수정·테스트: 위도 버킷 + bounding box. 서울 내·외 경계 예제, 비정상 좌표, 2,304개 참조 동치 테스트.

## 사용자 오류 처리

상한을 넘는 데이터는 공통 내부 코드 `ROUTE_DATA_TOO_COMPLEX`로 중단된다. UI는 내부 상세나 입력 데이터를 노출하지 않고 다음 안내만 표시한다.

- 제목: `이 지역의 경로 데이터가 너무 복잡해요`
- 안내: `더 가까운 장소를 선택해 다시 시도해 주세요.`
- 재시도: 동일 결정적 데이터에 대한 무한 재시도 버튼은 표시하지 않음
